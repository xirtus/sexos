# Chastity — round 173

Chastity now has a real Weft window (`apps/chastity`) and a reusable no_std vault
engine (`crates/chastity-core`). This branch depends on Weft PR #220 plus master;
its dependency base is the merge at dc4bbb8b. No kernel or existing owned app is
changed. Merge only after independent crypto review and green CI/QEMU evidence.

## What the app does

`run chastity` opens an unlock/create/import view. Type a master password; repeat
it when creating (minimum 12 characters). The unlocked view supports protected
username/password input, a 24-character cryptographic generator, adding entries,
loading/deleting a selection, and saving encrypted snapshots. Load then Add creates
a new entry; it does not overwrite the selected entry. Lock wipes credentials and
revokes autofill grants. Five minutes without input locks the vault; closing ends
the program. Unsaved changes are discarded on lock/close.

Credential keystrokes go into `Zeroizing<String>` before Weft input handling;
the toolkit receives only bullet masks, so password bytes never enter its undo,
redo, selection or clipboard buffers. Ctrl+A clears a protected field; Backspace
removes a character. Protected fields currently accept typing, not clipboard paste.
Titles and origins are ordinary visible metadata. Master passwords are held by
Shibari in the app's domain while unlocked, used in place during save, and wiped
on lock/close. Serialization, generated passwords and editable secret buffers are pre-sized to
avoid reallocations abandoning plaintext. AEAD uses detached in-place operations;
Argon2 uses an explicit zeroizing workspace, and gzip writes into a fixed bounded
zeroizing output buffer, including on decode/checksum failure.
Core entries, decrypted buffers and derived keys use zeroizing
storage; this is best-effort Rust memory hygiene, not a claim about registers or
all allocator/compiler copies.

## Storage and cryptography

A new snapshot uses fresh RDSEED entropy for its salt, 24-byte nonce and temporary
filename. There is no timestamp/counter entropy fallback; lack of RDSEED fails
closed. A file's fixed header holds the magic/version, Argon2id v1.3 costs, salt
and nonce. Production saves use 64 MiB, three iterations, one lane, and encrypt
with XChaCha20-Poly1305, authenticating the complete header as associated data.
Files are capped at 8 MiB, 4096 entries and 4096 bytes per field. KDF input limits
are checked before allocation: at most 256 MiB, 64 iterations, four lanes and one
GiB of memory-times-iterations work. These bound hostile input; UI work currently
runs synchronously and high-cost imports can pause input processing.

Saving exclusively creates a randomly named `.partial`, writes ciphertext, syncs,
exclusively renames to the requested *new* final name, then syncs again. Existing
snapshots are preserved, and failed saves may leave an encrypted `.partial` for
inspection. The caller must choose a fresh filename for each save. This avoids
claiming crash-safe replacement over Files' non-replacing rename API. File access
stays inside the program's granted Files folder; no ambient filesystem is added.
The name field accepts relative leaf names only. Changing the master password and
merging snapshots are not provided yet.

## KDBX import compatibility

The importer follows the [official KeePass KDBX specification](https://keepass.info/help/kb/kdbx.html).
It accepts password-only KDBX 4.0 and 4.1 with Argon2id or Argon2d v1.3, AES-256-CBC
or ChaCha20 outer encryption, optional gzip, and ChaCha20-protected XML fields.
Header and every block HMAC are verified before decrypting/decompressing XML. Gzip
output and XML node counts are bounded. The DOM parser sees only a same-length
masked XML copy, so its text/entity normalization cannot allocate credentials
outside the zeroizing buffers; original text is decoded by a bounded entity
decoder using preserved ranges. DTDs, CDATA, comments and non-declaration
processing instructions are refused. Title, URL, UserName,
Password and Notes are retained; historical entry versions are intentionally not
imported. Attachments and custom string fields are refused instead of dropped.

KDBX 3, AES-KDF, key files, external key providers, Salsa20-protected inner XML,
unsupported compression flags, and costs above the documented bound are unsupported.
Use a compatible password-only KDBX4 copy with standard fields when importing.
No source `.kdbx` file is modified. Imported entries remain in RAM until explicitly
saved under a new Chastity snapshot filename.

## Autofill boundary

`Session::approve` is called only after a trusted presenter obtains consent for
an exact origin, entry, caller domain and task identity. It returns a 30-second,
one-use opaque ticket. `redeem` requires that exact authenticated run identity and
uses credentials through a closure. Wrong-run guesses do not consume a legitimate
ticket. Lock, unlock and any mutable vault access revoke all tickets, preventing
entry-index substitution after an edit. No ambient lookup by origin is exposed.

This is an integration API, not a deployed cross-app service. The live PDX/mailbox
adapter, trusted consent surface and authority route for Multipass/Valentine remain
to be wired with their owners; client-supplied identity must never be trusted.
The current window does not advertise remote autofill as available.

## Evidence

`scripts/chastity_host_gate.sh` runs thirteen crypto/parser/authorization tests and
four UI tests: independent pykeepass-generated KDBX fixture import, wrong password,
tampering/truncation, authenticated vault header, fresh salt/nonce, bounded KDF,
generator refusal, pre-sized secret buffers, fixed zeroizing Argon2/decompression
workspaces, one-use exact-run grants, expiry/revocation, credential masks,
lock clearing and controls fitting 640x400. Fixtures contain only fictional test
accounts; `tests/fixtures/regenerate.py` documents their independent generation.

Independent review found and verified fixes for unwiped Argon2 workspaces,
plaintext reallocations, allocating AEAD helpers, gzip error output and XML parser
normalization copies. A post-fix read-only review reported no blocking findings;
this is not a third-party security audit.

The guest release build and forbidden-instruction scan pass locally.
`scripts/chastity_gate.py` drives the real Weft window through create, generate,
add, save, lock and wrong-password refusal, reboots QEMU, unlocks the persisted
snapshot and checks the entry count. Screenshots/serial are retained by Programs
CI. QEMU runtime evidence remains pending until that gate actually passes.
