# Drag: virtual machines on SexOS (W7 design, awaiting Andreas's decision)

Status: approved. Andreas approved the `SYS_VM` mechanism in section 3 and a kernel line
budget raise of about 1,200 lines for it on 2026-11-14. This is an exception to the
"only J and L touch `kernel/`" rule in DAILY_DRIVER_NEXT_100_SLICES.md, limited to the VM
mechanism. D1 is next; the budget row lands with the D1 code.

## 1. Goal

Run unmodified Linux and Windows guests at near-native speed, the way KVM + QEMU or
Hyper-V do, without moving a hypervisor's device emulation into ring 0. The guest is a
confined run like any other program: it holds only the caps it was given (memory, a disk
image, a network link, a window), and a hostile guest can reach nothing else.

## 2. Why it needs the kernel

Hardware virtualization (Intel VT-x, AMD SVM) is only reachable from ring 0:
`VMXON`/`VMLAUNCH`/`VMRESUME` (or `VMRUN`) are privileged, the VMCS/VMCB and the EPT/NPT
page tables point at physical memory, and VM exits arrive in ring 0. A pure ring-3
alternative exists (an x86 interpreter or a binary translator like QEMU's TCG), but it is
10 to 50 times slower and is not what Andreas asked for. It is noted as fallback F in
section 6.

## 3. The decision: a small VM mechanism in the kernel

Kernel side (mechanism only, about 900 to 1,200 lines including SVM):

| Piece | What it does |
| --- | --- |
| VMX/SVM enable | Per core, on first use: check CPUID/feature control MSR, `VMXON` region or `EFER.SVME` + host save area. |
| VM object | A capability naming one guest: its VMCS/VMCB pages, its EPT/NPT root, its vCPUs. Revocable like every other cap. |
| Guest memory | The VMM server lends pages it owns (the same lending window the IOMMU uses, `SYS_DMA_LEND` style) and the kernel maps them into the EPT at guest-physical addresses. The kernel never allocates guest RAM itself and refuses kernel pages and device BARs not leased to the caller. |
| vCPU run | One syscall op runs a vCPU until the next exit and returns the exit reason and a fixed register block to the VMM. Exits the kernel handles itself: external interrupts (host's), EPT misses for lent pages, preemption timer (so the scheduler keeps fairness). Everything else goes back to ring 3. |
| Interrupt injection | Op to queue an event for a vCPU (vector, type, error code); the kernel writes it at the next entry. Posted interrupts later. |
| PKU | Guest runs with its own CR4/PKRU in the VMCS; host PKRU restored on exit, so the guest can never use a host protection key. |

Proposed ABI: syscall 110 `SYS_VM` with ops CREATE, LEND_MEMORY, MAP, VCPU_CREATE,
VCPU_RUN, VCPU_GET/SET_REGS, INJECT, DESTROY. 110 is free (taken: 42-43, 50-69, 75,
80-87, 90, 100-101). It must be checked again at implementation time.

Kernel budget: the kernel is about 20,800 non-blank lines against the 21,500 budget, so
Drag needs a budget raise of about 1,200 lines with a row in the guardrails table. That
raise is the concrete thing Andreas approves.

## 4. Ring-3 side: the `drag` server

All of this stays out of the kernel, in a confined server per guest:

- Exit handling: I/O port and MMIO decode, CPUID/MSR policy, `HLT`, instruction emulation
  for MMIO (a small x86 decoder; the `iced-x86` crate, MIT, is a candidate).
- Platform: local APIC and IOAPIC emulation (x2APIC first), HPET or PIT, ACPI tables
  generated by Drag, PCI host bridge.
- Devices: virtio-blk (backed by a file or volume cap), virtio-net (backed by a SexNet
  link cap, NAT by default), virtio-gpu 2D into a SexOS window (3D later through sex-gl),
  virtio-input from the window's keyboard and mouse, virtio-snd into Bell, virtio-fs/9p
  for a shared folder grant.
- Firmware: Linux direct boot (bzImage + initrd, Linux boot protocol) first; UEFI guests
  via OVMF (BSD-2) for Windows.
- Reuse: rust-vmm crates (Apache-2.0/BSD: `vm-memory`, `virtio-queue`, `linux-loader`,
  `vm-superio`) adapted to the SexOS VM cap instead of `/dev/kvm`. That is adaptation into
  SexOS, not a Linux bridge: no Linux code runs.

## 6. Alternatives

- F (no kernel change): a ring-3 interpreter guest (in the style of QEMU TCG or Bochs). Works
  today under the guardrails, but slow; fine for old OSes and tests, not for daily Linux or
  Windows use.
- Linux via Tuxedo is not a VM and does not run Linux userspace programs; it stays a driver
  bridge only.
